# 📂 Документация по хранению данных в customDB

Мы берём упрощённый подход: **одна таблица = один файл** (например, `users.tbl`).

---

## 📝 Формат хранения строки

Каждая строка хранится так:

```
[ tombstone (1 байт) ] [ id (8 байт) ] [ длина записи (4 байта) ] [ JSON или сериализованные данные ]
```

- **tombstone = 0** → запись живая
- **tombstone = 1** → запись удалена
- **id** → уникальный номер строки
- **длина** → длина payload (например, JSON)
- **payload** → данные строки в сериализованном виде

### 📖 Пример
```
0|00000001|0018|{"username":"alice","age":23}
0|00000002|0016|{"username":"bob","age":30}
```

**Пояснение:**
- `0` = запись живая
- `00000001` = id=1
- `0018` = длина JSON (24 байта)
- дальше идёт сам JSON

---

## ➕ Как работает вставка

Пишем нового пользователя `charlie, 27`:

```
0|00000003|0019|{"username":"charlie","age":27}
```

Файл просто «растёт вниз» — новые записи добавляются в конец.

---

## ❌ Как работает удаление

Если удалить `bob`, мы не трогаем его строку, а просто ставим `tombstone=1`:

```
1|00000002|0016|{"username":"bob","age":30}
```

Теперь запись как бы «мертва», но всё ещё есть в файле → позже `compact()` перепишет живые строки в новый файл.

**Почему так?**
- ✅ Tombstone = быстро, надёжно, просто.
- ❌ Вырезание = медленно, сложно, опасно (нужно сдвигать байты).

---

## 🧹 Компактация (compact)

Со временем файл будет расти и накапливать «мёртвые» записи.  
Функция **`compact()`** — это уборка:

1. Берём все «живые» записи.
2. Переписываем их в новый чистый файл.
3. Старый файл удаляем.

### 🔑 Когда вызывать compact:
- Если доля tombstone > **30%**.
- Если размер файла > **100 МБ**.
- Либо вручную (метод `compact()`).

## 🔎 Как работает поиск

У нас есть индекс (например, `Map<Long, Long>`, где `id → смещение в файле`):

```
1 → смещение 0
2 → смещение 30
3 → смещение 60
```

### Алгоритм `get(2)`:
1. Движок смотрит в индекс: «id=2 находится по адресу 28».
2. Идёт в файл на смещение 28.
3. Читает заголовок записи.
4. Если tombstone=1 → запись удалена → вернуть `null`.
5. Если tombstone=0 → вернуть данные строки.

**Пример результата:**
```json
{"username":"bob","age":30}
```

---

## 📦 Структура записи в файле

Каждая запись состоит из 2 частей:

### 1. Заголовок (header) — бинарные поля фиксированной длины
- `tombstone` → 1 байт (0 или 1)
- `id` → 8 байт (`Long`)
- `длина payload` → 4 байта (`Int`)

📂 Эти данные всегда фиксированной длины → легко читать и быстро искать.  
Они нужны, чтобы СУБД поняла:
- жива ли запись,
- какой у неё id,
- сколько байт занимает payload.

### 2. Полезная нагрузка (payload) — переменная часть
Здесь лежит `Map<String, Any?>`, закодированная через `RecordCodec`.

Форматы могут быть разные: **JSON, BSON, MessagePack, Protobuf**.  
Длина payload хранится в заголовке.
